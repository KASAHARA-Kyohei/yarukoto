## 作っているもの

`yarukoto` というデスクトップアプリを作っています。

ざっくり言うと、ツリー型のアウトライナーを中心にしたプロジェクト管理アプリです。アイデア、メモ、決定事項、タスク、予定を同じツリーに置いて、そこからプロジェクト管理につなげることを目指しています。

最初に決めたのは、Jiraクローンにはしないことでした。

JiraやLinearのようなツールは強力ですが、個人開発や小さなプロジェクトでは、チケットを作る前の思考がけっこう散らばります。まだタスクとも言えないメモ、判断の途中にあるアイデア、決定事項、あとでやること。それらをいきなり「課題管理」の形に押し込むと、管理のための管理になりやすい。

なので `yarukoto` では、まずツリーで考えることを中心にしました。

現在の画面は、左にプロジェクト一覧、中央にワークスペースがある2ペイン構成です。中央には `Tree / Calendar / Report` のビューがあり、普段はTreeを見ながら操作します。ノード編集は常時表示のサイドバーではなく、必要なときだけモーダルで開きます。

この記事では、実装手順を細かく並べるというより、作りながら効いた設計判断をまとめます。

## 技術スタック

主な構成は以下です。

- Tauri v2
- React 19
- TypeScript
- Tailwind CSS v4
- shadcn/ui
- SQLite

Tauriを選んだ理由は、小さい業務アプリを作りやすいからです。Webフロントエンドの開発体験を使いつつ、配布できるデスクトップアプリにできる。今回のように「クラウド同期や認証はまだいらないが、ちゃんとローカルに保存したい」ものとは相性が良いと思います。

## 最初からSQLite保存にした

初期実装でありがちなのは、とりあえず `localStorage` に保存して、あとからDBへ移す流れです。今回は最初からSQLiteにしました。

理由は単純で、このアプリの中心が「長く使う思考の履歴」だからです。ツリー構造、並び順、日付、メモ、削除Undo、今後の検索やレポートを考えると、最初からDB前提にした方がよいと判断しました。

現在の中心テーブルは `nodes` です。

```sql
CREATE TABLE IF NOT EXISTS nodes (
  id TEXT PRIMARY KEY,
  parent_id TEXT NULL,
  title TEXT NOT NULL,
  type TEXT NOT NULL,
  status TEXT NOT NULL,
  memo TEXT NOT NULL DEFAULT '',
  start_date TEXT NULL,
  due_date TEXT NULL,
  sort_order INTEGER NOT NULL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```

ノードは `Group / Idea / Note / Decision / Task` のいずれかです。ステータスは `Inbox / Next / Doing / Done` に絞っています。

あえてテーブルを増やしすぎず、まずは1つの `nodes` に寄せています。ツリー型の思考整理では、種類ごとにテーブルを分けるより、「同じ場所に置ける」ことの方が大事だと考えました。

## UIからSQLを直接呼ばない

SQLiteは `@tauri-apps/plugin-sql` から扱っています。ただし、Reactコンポーネントから直接SQLは呼ばないようにしました。

間にRepository層を置いています。

```ts
export class NodeRepository {
  async listNodes() {
    const db = await getNodeDb();
    const rows = await db.select<DbNode[]>(
      "SELECT * FROM nodes ORDER BY parent_id IS NOT NULL, parent_id, sort_order, created_at",
    );
    return rows.map(toNode);
  }

  async createNode(input: CreateNodeInput) {
    // id, timestamp, sort_orderなどを組み立ててINSERTする
  }

  async updateNode(id: string, input: UpdateNodeInput) {
    // UIのcamelCaseをDBのsnake_caseへ変換してUPDATEする
  }
}
```

この分離はかなり効きました。

途中でUIは何度も変えています。3ペインから2ペインへ変えたり、右サイドバーを編集モーダルにしたり、Treeにミニガントを入れたりしました。それでも保存処理や並び替え処理を大きく崩さずに済んだのは、DB操作がRepositoryに閉じていたからです。

UI側では `startDate`、DB側では `start_date` のような変換もRepository周辺で吸収しています。小さいことですが、コンポーネントにDB都合が漏れないので、後から読みやすいです。

## ツリーを中心にする

このアプリで一番大事なのはTreeです。

最初は「プロジェクト管理アプリならガントチャートやカレンダーも必要では」と考えていました。ただ、実際に作ってみると、専用のガントタブを別に持つより、Treeの中に期間感が見える方が使いやすいと感じました。

今はTreeの行に以下を出しています。

- title
- type
- status
- progress
- period

`period` には `startDate -> dueDate` の軽量ミニガントを表示します。専用の大きなガントチャートではなく、Treeを読んでいる流れで「このタスクはいつ頃のものか」が分かる程度の表示です。

ここで大事だったのは、Treeを補助する表示に留めることでした。ガントを主役にしすぎると、今度はツリーで考える体験が弱くなります。

そのため、CalendarやReportもありますが、あくまで補助ビューです。日々の操作はTreeに寄せています。

## 3ペインから2ペイン + モーダルに変えた

初期は左・中央・右の3ペインでした。右側には選択ノードの詳細編集を常時表示していました。

これは最初は分かりやすいのですが、使っていると中央のTreeが狭くなります。特にミニガントや進捗をTreeに入れ始めると、横幅が足りなくなりました。

そこで、右のDetailペインをやめました。現在は左のProjectsと中央のWorkspaceだけにして、編集したいときだけモーダルを開きます。

結果として、普段見る画面がかなり軽くなりました。

この変更で気づいたのは、機能を増やすより、普段見えているものを減らす方がUXに効く場面があるということです。常に必要な情報と、必要なときだけ出ればいい情報を分けるだけで、操作の迷いが減ります。

## Vimライク操作とボタン操作を両立する

`yarukoto` では、キーボード操作をかなり重視しています。

Treeでは以下のような操作ができます。

- `j` / `k`: ノード選択
- `h` / `l`: 折りたたみ / 展開
- `a`: 子ノード追加
- `o`: 同階層の下に追加
- `Enter` / `i`: 編集モーダルを開く
- `dd`: 削除
- `J` / `K`: 上下移動
- `>` / `<`: 階層変更

ただし、Vim操作だけに振り切ってはいません。ボタンでも同じことができます。ショートカットが分からなくても使える状態にしておくのは、デスクトップアプリでは大事だと思っています。

また、`f` で画面上の操作対象にヒントを出してフォーカス移動できるようにしています。Vimiumのような考え方です。マウスを使わずにボタンや入力欄へ飛べるので、慣れると速いです。

一方で、入力欄にフォーカスしているときはショートカットが邪魔をしないようにしています。このあたりは地味ですが、壊れていると一気に使いにくくなります。

## 日付入力もキーボード寄りにした

開始日と終了日はGUIカレンダーで選べます。ただ、キーボード中心で操作していると、毎回マウスで日付を選ぶのは流れが切れます。

そこで日付入力はハイブリッドにしました。

- `Enter`: カレンダーを開く
- `i`: 直接入力
- `x`: 日付クリア
- カレンダー中の `h` / `l`: 前日 / 翌日
- カレンダー中の `j` / `k`: 翌週 / 前週
- `H` / `L`: 前月 / 翌月
- `t`: 今日へ移動

直接入力はまず `YYYY-MM-DD` のみにしています。相対入力の `+3d` や `today` も便利そうですが、最初から入れると仕様が膨らみます。まずは壊れにくく、説明しやすい形にしました。

## 進捗率は保存しない

Taskには進捗率を出しています。ただし、DBに `progress` カラムはありません。

進捗は派生値として計算しています。

- 葉Taskはstatusから計算
  - `Inbox`: 0%
  - `Next`: 0%
  - `Doing`: 50%
  - `Done`: 100%
- 子Taskを持つTaskは、直下の子Taskの平均
- Task以外は進捗なし

この仕様にした理由は、手入力の進捗率が意外と管理コストになるからです。

個人用の軽いPMアプリでは、進捗率を細かく入力するより、Taskを分解してDoneにしていく方が自然です。親Taskの進捗は子Taskから自動で見えれば十分だと考えました。

実装上も、保存値ではなく派生値にしておくと整合性を気にしなくて済みます。statusを変えたのにprogressを更新し忘れる、という問題がありません。

## 削除はUndoできるようにした

ツリー操作では削除が怖いです。親ノードを消すと子孫も消えるので、確認ダイアログを毎回出すとテンポが悪い。一方で、即削除だけだと危ない。

そこで、削除後に短時間だけUndoできる形にしました。

`dd` や削除ボタンでノードと子孫を削除し、削除前のスナップショットを一時的に持ちます。一定時間内なら元に戻せます。

この方式は、キーボード操作との相性が良いです。操作の速度を落とさず、失敗したときだけ戻せるからです。

## 実装を分けておいてよかったところ

作っていて一番助かったのは、関心ごとを早めに分けたことです。

現在は大きく以下のように分けています。

- `components`: UI
- `hooks`: 状態管理とショートカット
- `repositories`: SQLiteアクセス
- `domain/nodes`: ツリー整形、期間計算、進捗計算など
- `app`: focus hintや日付編集など、アプリ操作寄りのロジック

特に `domain/nodes` に純粋関数を寄せたのは良かったです。Treeの表示、期間バー、進捗率はUIと絡みますが、計算自体はReactから切り離せます。テストもしやすくなります。

UIを何度も変える個人開発では、最初から完璧な設計にする必要はありません。ただ、DBアクセスとドメイン計算だけは早めに分けておくと、後から画面を大きく変えやすいです。

## Tauriで作ってみて感じたこと

Tauriは、こういうローカルファーストな小型業務アプリにかなり向いていると感じています。

Webアプリとして作ると、認証、ホスティング、DB、同期、デプロイを考えたくなります。でも個人用ツールでは、そこまで要らないことも多いです。SQLiteに保存して、デスクトップで起動できれば十分な段階があります。

もちろん、配布や自動更新、OSごとの差異など、デスクトップアプリならではの課題もあります。それでも、ReactでUIを作りながらローカルアプリとして育てられるのは大きいです。

## まとめ

`yarukoto` は、思考整理ツリーを中心にした軽量プロジェクト管理アプリです。

作っていて特に効いた判断は次のあたりでした。

- 最初からSQLite保存にする
- UIからSQLを直接呼ばずRepository層を挟む
- Treeを中心にして、ガントや進捗は補助表示にする
- 常時Detailペインをやめて、編集はモーダルに寄せる
- Vimライク操作と通常操作を両方用意する
- 進捗率は保存せず、Task構造から派生表示する

まだ改善したいところはあります。CalendarやReportはもっと価値のある見せ方にできそうですし、配布まわりも詰めたいです。

ただ、ここまで作ってみて、Tauri + React + SQLite の組み合わせは「自分の作業に合わせて育てるデスクトップアプリ」を作るにはかなり良い選択肢だと感じています。
